# Правила работы в EmbedLinux

Эти инструкции применяются ко всему репозиторию. Перед изменениями прочитайте README в корне и в затрагиваемом разделе, проверьте `git status --short` и сохраните изменения пользователя.

## Назначение проекта

Репозиторий содержит практические туториалы по встраиваемому Linux. Общее описание и принципы должны оставаться независимыми от конкретной платы, дистрибутива и среды разработки. Платформы и инструменты выбираются для отдельных туториалов и явно указываются в них.

## Структура и платформы

- Главный `README.md` содержит описание проекта, навигацию и план туториалов.
- `hardware/README.md` содержит каталог аппаратных платформ с краткими описаниями и внешними ссылками.
- Описание каждой платформы находится в `hardware/<мнемоника>/README.md`.
- Второстепенные Markdown-документы размещайте рядом с основным README, используя подходящие по смыслу имена файлов. Не создавайте отдельный каталог только ради такого документа: например, инструкция Wi-Fi для `rpi0-2w` находится в `hardware/rpi0-2w/wifi-wpa3-sae.md`, а не в `hardware/rpi0-2w/wifi/README.md`.
- Каталог туториалов находится в `tutor/README.md`; материалы размещаются в `tutor/<тема>/`, например `tutor/native/`. Не добавляйте номера в имена каталогов или файлов туториалов. Порядок изучения и нумерацию задавайте в документах с оглавлением и ссылками: они могут меняться без переименования каталогов.
- Общая подготовка рабочего компьютера описывается в `environment/README.md`; туториалы ссылаются на неё и указывают собственные дополнительные требования.
- Используйте один `.gitignore` в корне репозитория. Не создавайте вложенные `.gitignore` в туториалах и примерах; общие правила не должны скрывать исходники и готовые конфигурации `.vscode`.
- Используйте короткие уникальные мнемоники из строчных латинских букв, цифр и дефисов. Принятое обозначение Raspberry Pi Zero 2 W — `rpi0-2w`.
- Мнемоника проекта не является именем хоста или официальным названием производителя. Аппаратную ревизию указывайте отдельно, если она влияет на пример.
- Каждый туториал размещайте в отдельном каталоге с README и необходимыми файлами примеров. При добавлении готового материала обновляйте соответствующий каталог и навигацию главного README.
- Планируемые материалы обозначайте как план. Не создавайте ссылки на ещё не существующие файлы.

## README и навигация

- Каждый README должен содержать раздел `Содержание` в начале документа с быстрыми внутренними ссылками на его разделы.
- Включайте в содержание заголовки второго уровня, кроме самого содержания. Подразделы добавляйте, когда это помогает ориентироваться в длинном документе.
- Используйте якоря, соответствующие Markdown-заголовкам. После переименования или перемещения разделов обновляйте содержание и ссылки на них.
- Не смешивайте содержание документа и план будущих туториалов: это отдельные разделы.
- Внутри репозитория используйте относительные ссылки на реальные файлы. В README платформ и вложенных разделов добавляйте ссылку к родительскому README.

## Стиль и практические примеры

- Используйте единый нейминг: `host` — компьютер разработчика, `target` — целевое устройство; параметры SDK — `SDK_*`, параметры локального проекта — `HOST_*`, устройства — `TARGET_*`, общие параметры сборки `BUILD_TYPE` и `BUILD_JOBS`. В нативном примере VS Code использует настройки `target.*` / `build.*` и относительные компоненты путей. В кросс-примере `sdk/environment-setup` и `project.env` экспортируют окружение для Bash. VS Code содержит отдельную копию параметров в `settings.json`, читает `${config:...}` и передаёт переменные скриптам через `options.env`; поддерживайте обе конфигурации согласованными. Формируйте абсолютные пути в окружении из родительских переменных. На target при кросс-сборке `TARGET_WORK_DIR` — каталог установки; `TARGET_BUILD_DIR` не нужен. Имена проектов и приложений фиксируйте в `project/CMakeLists.txt`, без внешнего переименования. Компиляторы и архитектуру задавайте в toolchain-файле CMake. Определения приведены в `environment/README.md`.
- Документацию пишите по-русски, просто и технически точно. Объясняйте необходимые термины; избегайте лишних подробностей и категоричных обобщений.
- Простые задачи VS Code, вызывающие одну операцию, называйте с суффиксом `Only` (`Build Only`, `Deploy Only`). Составные задачи называйте по назначению без префиксов (`Build`, `Deploy`, `Debug`).
- Для каждого туториала указывайте задачу, ожидаемый результат, предварительные условия, действия и способ проверки.
- Явно обозначайте, где выполнять команды и создавать файлы: на рабочем компьютере или в целевой системе. Различайте Bash, PowerShell и другие оболочки.
- В учебных файлах окружения используйте явные присваивания `export NAME=value`, без подстановок запасных значений `${NAME:-value}`. Зависимые пути формируйте из ранее заданных переменных.
- Для параметров окружения указывайте конкретный файл, имя параметра и пример значения. Различайте локальные пути и пути целевой системы.
- В конце разделов с настройкой приводите полное содержимое готовых конфигурационных файлов, а не обрывки JSON или указания «добавьте где-нибудь». Если в репозитории есть готовые файлы, давайте ссылки на них и поддерживайте совпадение с примерами в README.
- Разные способы работы, например нативную сборку и кросс-компиляцию, оформляйте как самостоятельные последовательности действий.
- Различайте возможности процессора, архитектуру ядра и архитектуру пользовательских приложений и библиотек. Подбирайте toolchain под целевое приложение и доступное оборудование.

## Источники и проверка

- Характеристики аппаратных платформ и меняющиеся сведения проверяйте по актуальным первичным источникам: документации производителя и официальной документации инструментов.
- Размещайте внешние ссылки рядом с подтверждаемыми сведениями. Не выдавайте рекомендации или предположения за требования производителя.
- Перед завершением проверьте внутренние якоря, относительные ссылки, корректность конфигураций и совпадение примеров с файлами.
- Выполняйте проверки, соответствующие изменениям. Для правок текста достаточно проверки навигации и `git diff --check`; для изменённых примеров сборки проверьте их доступными инструментами.
- Указывайте границы проверки: сборка на компьютере не подтверждает запуск и отладку на целевом устройстве.
